I agree with most of this analysis, but I would separate the architectural enhancement from the current production incident.

1. The code analysis is correct

From your code:

const cleanCallee = (rawCallee.startsWith('2060') && rawCallee.length >= 14)
  ? rawCallee.slice(4)
  : rawCallee;

and your production data:

20609231864220910
20608801672262958

it's clear that:

the full routing number arrives from Asterisk,
the 2060 prefix is preserved in the database,
but pickBestRule() deliberately strips it before rule matching.

That part is confirmed.

2. The current implementation is hard-coded

Today the logic effectively says:

2060 + destination
        ↓
remove 2060
        ↓
match only destination

So today:

2060923...

matches:

923
3. The proposed enhancement is good

Adding:

routing_prefix

to the governance rule is a clean design.

I'd actually make it configurable instead of hardcoding:

const KNOWN_PREFIXES = ['2060','2061','2062'];

because six months from now you'll add another product.

Instead I'd prefer:

call_governance_products

id
product_name
routing_prefix
enabled

Then the rule references the product instead of embedding routing knowledge in code.

4. One thing I would change

I would not score based on string length.

Instead I'd use explicit priority.

Example:

Routing Prefix
      ↓
Destination Prefix
      ↓
Caller Prefix
      ↓
Channel Pattern

If routing prefix doesn't match:

continue;

No scoring required.

That makes the matching deterministic and much easier to maintain.

5. This is NOT today's production outage

This is the important distinction.

Adding routing-prefix support will not restore live governance.

Those are two separate topics.

Today's production issue is still:

No new Bridge events
↓
No new governed_calls
↓
No active governance

Whether rules match on:

2060
923
880
12234

doesn't matter if no calls are reaching the governance Asterisk.

So I completely agree with the conclusion:

Multi-product governance is a future enhancement.

It should not be mixed into the incident response.

My recommendation

I would implement this as Phase 2 after production is stable.

Phase 1 (Production recovery)
Restore OTP routing through the governance Asterisk.
Confirm governed calls are being inserted again.
Verify timers, playback, BYE, and CDR reconciliation.

Freeze governance logic once that is working.

Phase 2 (Architecture)

Extend the rule model to support products.

Example:

Product	Routing Prefix	Destination	Timer
Wholesale	2060	923	7 s
VOTP	2221	923	59 s
Premium	2061	923	120 s

Then the NOC can manage governance by product, which is exactly the flexibility you've been aiming for.

Overall, I think you've identified a valuable enhancement. I would just keep it separate from the current outage investigation so that restoring production traffic remains the top priority.
