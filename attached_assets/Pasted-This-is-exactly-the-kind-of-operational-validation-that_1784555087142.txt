Assessment

The duplicate-batch policy you've implemented is well aligned with the period-first architecture.

Policy

One active billing batch per billing period.

Allowed states:

✅ Create a new batch if none exists.
🚫 Block creation if an active batch already exists with work.
✅ Allow regeneration after cancellation.
✅ Ignore historical empty batches (0 jobs).

That's deterministic and operationally clear.

The runtime issues you uncovered are valuable

These are the kinds of issues that only appear under operational testing.

1. Empty batch shouldn't block

You discovered that an old batch with:

0 jobs

was still considered active.

Treating empty batches as non-blocking is the correct behavior.

2. FK fallback bug

This is a genuine implementation defect that would have been difficult to spot in static review.

Changing:

0

to

NULL

for optional foreign keys is the correct fix because:

0 is not a valid parent row.
NULL correctly represents "no reconciliation reference."
3. Re-run job lifecycle

This is probably the most important operational discovery.

You found:

Cancelled batch

↓

Jobs remained PENDING

↓

Unique index prevented regeneration

The fix:

cancel (or otherwise retire) the old pending jobs before creating replacements,

is consistent with your business rule that a cancelled batch should no longer block a new billing run.
