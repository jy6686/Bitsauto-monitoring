The debugging process often followed this pattern:

Symptom
      ↓
Possible cause
      ↓
Code change
      ↓
Next hypothesis
      ↓
Another code change

instead of:

Symptom
      ↓
Collect evidence
      ↓
Prove root cause
      ↓
Minimal fix
      ↓
Validate

On a production telecom platform, the second approach is much safer.

Going forward

For BitsAuto, I would adopt a strict rule:

No production code change unless the evidence directly supports it.

For example, before changing governance matching:

Capture one failing call.
Record:
Bridge event
Channel names
Rule selected
Regex result
Reproduce locally.
Apply the smallest possible fix.
Re-test the same scenario.

That avoids broad edits based on assumptions.

I think the experience reinforces the production-first approach you've been following for BitsAuto:

Make small, evidence-backed changes.
Validate each change against live data.
Avoid broad refactors or multiple speculative fixes in one step.
Keep a rollback path for every production change.

That approach minimizes the kind of churn and wasted effort you've experienced over the last couple of days.
