I think this is a good next diagnostic step, with one refinement.

The proposed commands are trying to answer one binary question:

Is Asterisk actually receiving INVITEs from Sippy?

That's exactly the right question to answer now. However, I'd prioritize the checks slightly differently.

1. Capture SIP traffic first (highest value)

Run this while placing a single test call:

timeout 30 tcpdump -nn -s0 -A -i any 'host 191.101.30.107 and udp port 5060'

If Asterisk receives an INVITE, you'll see something like:

INVITE sip:20608801319653537@159.223.32.59 SIP/2.0

Possible outcomes:

INVITE appears → network path is good; investigate Asterisk dialplan/endpoints.
Only OPTIONS appear → Sippy is not sending call traffic to this server.

That is the most valuable test.

2. Check the Asterisk log at the exact timestamp

Good suggestion:

grep "14:58:4" /var/log/asterisk/full

If tcpdump shows an INVITE but full has nothing, then we investigate logger configuration or packet handling.

If both are empty, Asterisk never received a call.

3. Check logger configuration

Also worthwhile:

cat /etc/asterisk/logger.conf

Make sure the full log includes at least:

notice
warning
error
verbose
debug

or similar.

4. Check fail2ban/security log

This is lower probability, but easy to eliminate:

grep "191.101.30.107" /var/log/asterisk/fail2ban

I actually think this is unlikely, because:

your SIP peer qualifies every minute,
sip show peer sippy reports OK,
and the source IP is already trusted for OPTIONS.

If fail2ban were banning 191.101.30.107, you'd usually see qualification failures too.

5. Verify whether only OPTIONS are arriving

This is the key.

If during a live test you capture:

OPTIONS
200 OK
OPTIONS
200 OK

and no INVITE, then the investigation shifts completely to Sippy.

At that point, the remaining questions are:

Does Route Group 880/923 actually select Connection 16?
Does Connection 16 still point to 159.223.32.59?
Is it using 5060 or 5160?
Is another connection named asterisk(in) being selected instead?
My assessment

Based on everything you've gathered over the last several hours:

✅ Asterisk is listening on both 5060 and 5160.
✅ sippy peer is healthy.
✅ OPTIONS exchanges are successful.
✅ Dialplan exists and matches _2060X..
❌ No channels are created.
❌ No Bridge events occur.
❌ No INVITEs appear in the normal logs.

That makes the probability increasingly high that the issue is before the call reaches Asterisk, not inside Call Governance.

I would put the current probabilities at:

80% – Sippy routing/connection selection (Connection 16, route group, or gateway selection).
15% – INVITEs reach Asterisk but are rejected before dialplan execution (logger/tcpdump will prove this).
5% – Remaining Asterisk configuration issue.

I would not make any more changes to BitsAuto or Call Governance code until this SIP-level question is answered, because the evidence is now pointing much more strongly at the call delivery path than at the governance application itself.
