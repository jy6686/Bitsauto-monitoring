I think you've identified the actual conceptual problem. There are three different concepts that have been mixed together:

Platform/System Roles (RBAC) – what a user is allowed to do.
Departments – which business function they belong to.
Portals/Workspaces – the UI experience they use.

Those should not be represented by the same Role enum.

I would redesign it like this
1. System Role (RBAC)

This answers "What can this user do?"

export type SystemRole =
  | "super_admin"
  | "admin"
  | "routing_admin"
  | "destination_manager"
  | "operator"
  | "approver"
  | "viewer";

This should remain small and stable.

Examples:

Can approve?
Can edit routing?
Can push to Sippy?
Can manage users?

These are security permissions.

2. Department

This answers "Which business unit does this user belong to?"

export type Department =
  | "finance"
  | "noc"
  | "commercial"
  | "kam"
  | "engineering"
  | "fraud"
  | "management";

This is not RBAC.

It drives:

default dashboard
reports
notifications
ownership
queues
3. Portal (Workspace)

This answers "Which portal should open?"

export type Portal =
  | "finance"
  | "noc"
  | "kam"
  | "partner"
  | "client"
  | "engineering"
  | "management";

Exactly what you've been building.

For example:

Finance Portal

is not a role.

It's a workspace.

Then one user becomes
{
  systemRole: "viewer",

  department: "finance",

  portal: "finance"
}

or

{
  systemRole: "routing_admin",

  department: "engineering",

  portal: "engineering"
}

or

{
  systemRole: "viewer",

  department: "kam",

  portal: "kam"
}
Permissions become much cleaner

Instead of

Role = finance

you get

SystemRole = viewer

Department = finance

Then

Finance Portal

↓

Billing
Invoices
Credit Notes
Payments
Revenue

without inventing another RBAC role.

Why you're getting 496 errors

Right now the code mixes all three.

Example:

ROLE_PATHS

contains

finance
kam
noc

Those aren't security roles.

They're portals.

So TypeScript complains because the canonical Role no longer includes them.

I would introduce three separate enums

Instead of

Role

I'd have

SystemRole
Department
Portal

Then:

ProtectedRoute

checks

SystemRole

while

WorkspaceShell

uses

Portal

and

Notifications
Ownership
Reports

use

Department
This also fits your long-term roadmap

You've already built or planned:

NOC Portal
Finance Portal
KAM Portal
Client Portal
Partner Portal
Management Portal

Those are portals, not security roles.

Similarly:

Finance
NOC
Commercial
KAM

are departments.

While:

Admin
Routing Admin
Destination Manager
Viewer

are RBAC permissions.

Keeping those three concepts separate will make the architecture much easier to extend as you add more portals and department-specific features. It will also eliminate the need to overload a single Role type with unrelated meanings.
