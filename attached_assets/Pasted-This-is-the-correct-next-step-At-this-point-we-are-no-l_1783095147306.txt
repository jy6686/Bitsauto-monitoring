This is the correct next step. At this point we are no longer guessing—we need to see the SIP dialogue between Asterisk and Sippy.

A few observations first:

1. sip show registry showing 0 registrations is normal

Your peer is configured by IP (ToHost: 191.101.30.107) with:

Dynamic : No
Insecure: port,invite

So there is no SIP REGISTER. The Status: OK (198 ms) from sip show peer sippy is the important part. That confirms Asterisk can reach Sippy via OPTIONS.

2. Now enable SIP debugging correctly

Inside the Asterisk CLI (not Linux shell):

sip set debug peer sippy

or, if your version doesn't support peer:

sip set debug on

Then place one test call.

3. What you are looking for

The most important lines will be something like:

Reliably Transmitting (NAT) to 191.101.30.107:5060:
INVITE sip:222118801935700194@191.101.30.107 SIP/2.0

Then immediately afterwards you'll receive one of these from Sippy:

Response	Meaning
100 Trying	Sippy accepted the INVITE
180 Ringing	Vendor is ringing
183 Session Progress	Media path established
200 OK	Call answered
403 Forbidden	Authentication / ACL problem
404 Not Found	Prefix or destination rejected
480 Temporarily Unavailable	Routing problem
486 Busy Here	Busy
503 Service Unavailable	Sippy routing failure

That SIP response will tell us exactly where the call is stopping.

One thing caught my eye

Your dialplan is sending:

Dial(SIP/sippy/222118801935700194)

The original called number was:

20608801935700194

So Asterisk transforms it into:

22211 + 8801935700194

That means:

2060 is stripped
22211 is added

This matches the design you've previously described:

2060 = inbound commercial routing prefix from Sippy to Asterisk
22211 = outbound Voice OTP product prefix from Asterisk back to Sippy

So the dialplan logic itself looks consistent.
