Yes, I think this is a sensible point to pause portal expansion.

What you've discovered is not really a portal UI problem anymore—it's an identity and access flow problem.

Right now:

A user can manually remove /noc from the URL and return to the main application.
There is no concept of "this user belongs to the NOC Portal" versus "this user has access to the full platform."
Portal navigation is ahead of the authentication and authorization layer.

That means continuing to build more portal features before establishing the login and access model is likely to create rework later.

I would change the implementation order
Phase 1 — Login & Identity Foundation (highest priority)

Build the enterprise login first.

After authentication, the system should determine:

Who is the user?
What portals are assigned?
Do they have full-platform access?
Which portal should they land in?

For example:

Login
    ↓
Authenticate
    ↓
Load User Profile
    ↓
Load Portal Assignments
    ↓
Load Permissions
    ↓
Redirect
Phase 2 — Access Control

Add an access model such as:

Platform Access
    • Full Platform
    • Portal Only

Then assign users accordingly.

Examples:

User	Access	Landing
Super Admin	Full Platform	/
NOC Manager	NOC Portal	/noc
Commercial VP	Commercial Portal	/commercial
Finance Manager	Finance Portal	/finance
Viewer	Assigned Portal	Assigned Portal

Once a user is in a portal:

If they try to browse to:

/

or

/calls

the application should enforce the access policy.

For a portal-only user:

/calls
      ↓
Unauthorized
      ↓

      ↓
/noc/live-calls

or simply return an access-denied page if the route is outside their assigned portal.

This closes the gap you've identified.

One adjustment to our earlier plan

Previously, we discussed keeping the current login behavior and adding portal-aware redirects later. Given what you've now observed during end-to-end testing, I think it's reasonable to bring the login foundation and portal-aware access forward before expanding the NOC Portal further. The key is to keep this scoped to the authentication foundation and access flow, rather than expanding into broader IAM features all at once.

I would keep the scope limited to:

Enterprise login page
Authentication
Portal assignment lookup
Full Platform vs Portal Only access
Default portal redirect

I would not yet implement:

Those can follow once the login foundation is stable.

I think this sequencing reduces the chance of rework and gives you a solid security foundation before investing more effort in the individual portals.
