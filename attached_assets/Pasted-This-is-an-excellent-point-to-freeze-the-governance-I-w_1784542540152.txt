F3 Architecture Review

I agree with the three implementation rules.

Rule 1 — Read-only Consumer

This is exactly how reconciliation systems should behave.

Reconciliation should identify differences—not modify the financial source of truth.

Rule 2 — Explainability First

Making reason_code mandatory is particularly valuable.

Instead of:

Difference = $12.30

the platform should explain:

Rating Difference
Grace Period
Free Seconds
Currency Conversion
Manual Adjustment
Missing Vendor Cost
Billing Cycle Cutoff

That makes reconciliation actionable for Finance teams.

Rule 3 — Immutable Evidence

This is the strongest architectural decision in the contract.

Using a lineage like:

materialization_runs
        │
        ▼
reconciliation_runs
        │
        ▼
ai_scan_runs
        │
        ▼
ai_findings

creates a complete audit trail.

Blocking cascade deletes protects historical evidence, which is particularly important in telecom environments where disputes and audits may occur months later.

One recommendation before F3 begins

Since you're defining immutable evidence, I'd make the evidence records version-aware.

For example:

snapshot_version

reconciliation_version

detector_version

rule_version

If an AI detector changes in the future, you'll still know exactly which logic produced historical findings.

This becomes invaluable when comparing historical scans across software releases.

Suggested F3 certification gate

I'd add one explicit criterion to the F3 certification template:

Evidence Reproducibility

Given:

Snapshot X
Reconciliation Run Y
AI Scan Z

Running the same reconciliation and AI logic again against the same snapshot should produce identical findings (unless the detector version intentionally changes).

That demonstrates determinism, which is important for auditability.
