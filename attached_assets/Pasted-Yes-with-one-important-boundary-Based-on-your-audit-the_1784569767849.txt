My recommendations on your two questions
1. CEO / HOD edge case

Recommendation: Do not create a bypass.

Always use the same hierarchy resolution function.

getVisibleAccountIds(userId)

For a CEO/HOD, the traversal naturally returns the entire organization.

Advantages:

One code path for every role.
Easier to test.
Easier to audit.
No special cases.
Future reorganizations work automatically.

The performance difference is usually negligible compared to the complexity introduced by a bypass. If performance ever becomes an issue, optimize internally (caching, recursive SQL, materialized paths), not by changing the authorization logic.

So the rule becomes:

Every Commercial user is resolved through the hierarchy. CEO/HOD simply happens to have the largest subtree.

2. Users without a KAM record

I would separate system administrators from Commercial users.

There are really three categories.

A. Commercial users

Examples:

KAM
Team Lead
Manager
VP
HOD

These must have a linked kams.userId.

If they don't:

Commercial Portal
        ↓

That is a configuration error, not something to silently work around.

B. Platform administrators

Examples:

super_admin

These are infrastructure roles.

They may need to inspect Commercial data for support, testing, or troubleshooting.

I would give them an explicit capability such as:

Then the hierarchy service becomes:

if (hasPermission("commercial.view_all_accounts")) {
    return ALL_ACCOUNTS;
}

return resolveHierarchyScope(userId);

Notice this is permission-based, not role-name-based.

That makes it extensible and consistent with the authorization model you've already built.
